# 의정의 흐름 개발 공통 지침

기준일: 2026-10-22, Asia/Seoul. 사용자가 요청한 개발 방식 진단과 우선순위 재정리를 반영한다. 문서 작성 완료와 기능 구현·공개·실행 중 작업의 전환 완료는 별개다.

## 1. 제품 방향과 이번 목표

**제품:** 정치에 조금이라도 관심 있는 사람이 화제 이슈를 발견하고, 배경·경과·쟁점과 확인된 근거를 이해하며, 이후 변화를 다시 확인하는 앱.

**핵심 흐름:** 화제 순위 또는 검색 → 이슈 해설 → 인물·원문 근거 → 읽던 문장 복귀 → 후속 확인.

**이번 목표:** 대표 이슈 한 개를 실제 검토·공개 가능한 자료로 연결해 위 흐름을 끝까지 사용할 수 있게 한다. 전체 인물·법안·정책을 먼저 수집하는 것은 선행 조건이 아니다.

유지할 결정:

- 홈은 **화제 이슈 순위 중심**이다. 읽기 화면은 기존 **A · 해설 노트**의 흰 바탕·절제한 색·짧은 설명을 유지한다. 두 결정은 진입과 읽기라는 서로 다른 역할이다.
- 초보자도 이해하도록 배경·현재 단계·아직 모르는 내용을 설명한다. 사실·당사자 주장·공식 판단과 각각의 날짜·범위를 구분한다.
- 초기에는 주요 이슈를 충분히 설명하며 확장한다. 무료 공개로 이해도·신뢰·반응을 확인한다.
- AI가 자료·초안을 준비하고 운영자가 원문·핵심 내용을 검토한다. 새로운 내용·변경 내용을 과거 원고 승인에 포함시키지 않는다.
- 월 서비스 운영비 상한은 기존 합의한 **5만 원**이다. 마케팅 캠페인의 **4주 현금 예산 10만 원**과 별도로 관리한다. 미확인 비용은 0원으로 처리하지 않는다.
- 직접 운영·매일 1건이라는 의지를 유지하되, 새 원고·기존 이슈 갱신·정정의 작업량과 실제 검토 시간을 기록한다. 중요한 정정은 신규 제작보다 먼저 처리한다.
- 기존 하루 15~20분은 마케팅 운영 계획의 기준이다. 전체 앱 개발 시간이나 모든 이슈의 검토·갱신 시간까지 확보됐다는 뜻으로 사용하지 않는다.

## 2. 공통 기준 문서

| 목적 | 기준 |
| --- | --- |
| 제품·개발 운영 원칙 | 이 문서 |
| 현재 할 일·담당·의존성·보류와 재개 | [첫 대표 이슈 개발 계획](../plans/2026-10-22-first-issue-release.md)의 공통 작업표 |
| 편집·정정·공개 평가 | [기존 편집 정책](editorial-policy.md) |
| 제품 소유자와의 기존 합의 | [기획 브리프](../design/2026-10-17-redesign/discovery-brief.md) |
| 실제 공개 연결·성과 측정 상태 | [공개 준비 기록](../marketing/beta-4w/readiness.json)과 각 항목의 시각이 있는 증거 |

과거 계획과 검증 보고서는 삭제하지 않는다. 과거 문서의 시점값·전체 구현 목록을 현재 작업 순서로 사용하지 않는다. 상태 파일과 최신 실행 기록이 다르면 각각의 관측 시각·근거를 대조하고, 확인 전에는 현재 상태를 단정하지 않는다.

새로운 사용자 직접 지시는 기존 결정을 변경할 수 있다. 그때 변경 이유, 이번 목표에 미치는 영향, 대신 미룰 작업을 공통 작업표에 남긴다. 승인·보안·편집 조건은 실제로 적용되는 범위에서 유지하며, 이미 받은 승인을 반복 요청하지 않는다.

## 3. 작업을 선택하는 순서

1. 공개 중인 잘못된 내용·신원 연결·자료 노출·데이터 손실 등 확인된 문제를 처리한다.
2. 이번 대표 이슈 흐름을 막는 가장 앞선 장애물을 해결한다.
3. 해당 흐름의 회귀·접근성·유지보수 문제를 해결한다.
4. 기능 확대·추가 조사·일반 최적화는 보류 목록에 둔다.

수집량, 화면 수, 테스트 수, 보고서 수는 보조 정보다. 작업을 시작하려면 다음 네 문장을 채운다.

```text
작업 ID / 담당:
해결할 사용자 행동과 현재 장애물:
기존 구현을 재사용할 위치 / 변경 범위:
완료를 확인할 실제 시나리오와 증거:
```

한 번에 진행하는 **제품 목표는 하나**다. 같은 목표 안에서 계약이 정해진 서로 다른 모듈은 병행할 수 있다. 같은 파일의 동시 수정과, 의존 작업이 끝나지 않은 상태의 별도 기능 확장은 피한다.

## 4. 채팅별 책임

| 담당 | 이번 책임 | 먼저 받거나 전달할 것 |
| --- | --- | --- |
| 이 계획을 관리하는 채팅 | 우선순위·범위·장애물·전체 완료 판정 | 작업표와 담당별 증거를 통합 |
| 「백엔드」 | 대표 이슈에 필요한 공개 데이터·ID·근거·검토/공개 경로와 읽기 계약 | 공개 가능한 자료 목록, 정확한 ID·버전·경로·미공개 이유 |
| 「디자인 & 프론트」 | 모바일·웹 읽기 연결, 순위 진입, 근거·인물 왕복과 복귀, 모바일 검증 | 고정된 콘텐츠/공개 계약과 실제 정상 데이터 |
| 「마케팅」 | 대표 이슈의 설명·공식 원문 대조, 기존 게시물 정정 확인, 정확한 이슈 링크·소수 사용 관찰 준비 | 운영자 내용 검토, 실제 공개 주소와 검증 결과 |
| 보조 디자인·조사 작업 | 기존 레퍼런스에서 이번 화면에 채택할 구성과 이유를 전달 | 프론트 통합 담당에게 적용 위치·전후 차이·검증 기준 전달 |

기존 디자인 관련 채팅에서 동일 홈·라우팅·스타일 파일을 별도로 재구현하지 않는다. 「디자인 & 프론트」가 변경을 통합한다. 소유한 파일 밖의 변경이 필요하면 담당과 작업표에 의존성을 먼저 남긴다.

문서 공유만으로 다른 채팅에 메시지가 전달되거나 실행 중 작업이 전환됐다고 표시하지 않는다. 담당이 공통 문서를 읽고 착수 작업을 기록하면 전환 확인으로 남긴다.

## 5. 데이터·공개 경계

- 화제 순위는 **무엇을, 어느 기간, 어떤 출처 범위에서 집계했는지와 갱신 시각**을 보여준다. 기존 radar의 규칙 기반 점수를 검증된 국민 관심도·사실성·지지도로 표현하지 않는다.
- 편집자 선정 해설과 실제 집계 순위를 구분한다. 대표 이슈를 시험하기 위해 가짜 순위를 부여하거나 키워드만으로 다른 사건에 연결하지 않는다.
- 뉴스 후보, 검토된 이슈 해설, 법안·발언 등 원자료, 인물 문서는 역할이 다르다. 실제 이슈 ID와 승인된 연결 근거를 정해 연결한다.
- 비공개 GraphRAG 후보·SQLite·운영자 API를 앱에 노출하지 않는다. 이름 일치만으로 인물·역할·표결을 확정하지 않는다.
- 웹의 기존 검토 해설을 재사용하되 수정·추가 원고와 인물 연결의 승인을 별도로 확인한다. `reviewed` 표식만 복사해 새 사실을 승인된 것으로 만들지 않는다.
- 기존 원문·검토·공개 버전과 정정 이력을 보존한다. 공개 API 실패를 예시 자료나 정상 빈 결과로 바꾸지 않는다.
- 기존 편집 정책의 공개·평가 조건은 유지한다. 대표 이슈 한 개의 통과로 더 넓은 AI 결과의 평가나 정책상의 미완료 항목이 통과했다고 해석하지 않는다.

## 6. 조사·수집·자동화의 경계

조사는 이번 작업에서 결정해야 할 질문 하나를 정하고 시작한다. 기존 레퍼런스를 먼저 쓰고, 추가 조사 결과는 **채택할 안·이유·적용 위치·종료 판단**으로 끝낸다. 후보·캡처 수만 늘리고 종료하지 않는다.

새 수집원·새 모델·전국 범위 확장·새 커뮤니티 생성 방식·대시보드 기능 확대는 대표 흐름에 필요한 이유가 없으면 보류한다. 이미 승인받은 수집은 기존 범위·한도·기한 안의 유지 작업과 신규 개발을 구분한다.

**이 계획은 실행 중 수집기·추론 작업·자동화·인스타 예약을 실제로 중단하거나 수정한 기록이 아니다.** 담당은 전환 전에 실제 프로세스·명령·체크포인트·진행 중 원격 작업을 확인하고 보존한다. 기존 승인 범위를 넘는 중단·재시작·공개·게시·비용 변경의 권한을 이 문서에서 추정하지 않는다. 승인된 작업은 불필요한 재확인 없이 그 범위에서 진행한다.

자동화는 실행될 때 공통 목표와 담당 작업 ID를 확인한다. 기존 저장 프롬프트와 이번 계획이 충돌하면 충돌 범위와 필요한 전환 작업을 기록한다. 저장 프롬프트를 바꾸기 전에는 자동화 전환 완료로 표시하지 않는다.

## 7. 완료·검증·보고

완료 증거는 다음을 구분한다.

| 구분 | 확인하는 것 | 대신할 수 없는 것 |
| --- | --- | --- |
| 구현·합성 계약 검사 | API·상태·상호작용의 재현 가능한 동작 | 실제 공개 자료의 정확성과 제공 상태 |
| 실제 공개 자료 검사 | 같은 이슈의 해설·인물·근거 전체 흐름 | 실물 기기 품질·사용자 이해 |
| 모바일 브라우저·에뮬레이터 | 360/412px·큰 글자·뒤로가기·복귀 | 실물 Galaxy·사용자 관찰 |
| 외부 주소 검사 | 다른 기기에서 로그인 없이 같은 이슈 읽기 | 장기 가용성·실제 재방문 |
| 실제 독자 관찰 | 배경·현재 단계·근거 이해와 막힌 지점 | 전체 시장 성과·장기 유지율 |

현재 변경에 맞는 기존 테스트를 실행하고 보호된 검증을 약하게 바꾸지 않는다. 같은 검사를 이유 없이 반복하거나 낮은 영향의 문서 변경에 새 제품 테스트를 만들지 않는다. Python 변경은 타입 힌트·Google 스타일 docstring·Black/isort·파일당 500줄 미만을 지킨다.

보고는 다음 순서로 짧게 작성하고 공통 작업표를 갱신한다.

```text
작업 ID / 상태 / 관측 시각:
이제 사용자가 실제로 할 수 있는 일:
아직 못 하는 일과 현재 장애물:
확인한 환경·증거와 미검증 범위:
다음 작업 ID / 담당 / 필요한 인계:
```

새 요청은 현재 목표에 필요한지 분류한다. 필요하면 기존 작업에 통합하고, 별도 확장이면 보류 목록에 이유·재개 조건을 남긴다. 사용자에게 선택이 필요한 경우 선택지가 현재 작업·일정에 미치는 영향을 구체적으로 제시한다. 이미 결정된 방향의 반복 인터뷰는 하지 않는다.
